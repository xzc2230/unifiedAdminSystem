# 应用共享权限设计

用户已确认：原创建者保留权限，接收者可以查看和编辑；普通用户只看到自己创建和明确共享给自己的应用，平台管理员管理当前有效租户内的应用。

## 权限与范围

保留 pkg_resource_owner 和业务 user_id，不再通过“转移”覆盖归属。新增 pkg_app_share，以 tenant_id、app_id、grantee_user_id 唯一登记共享。共享只扩大应用本身的查询、详情、导出、编辑范围，不授予删除、共享管理、再次转授、日志或关联资源权限。操作仍需角色菜单/按钮权限，编辑仍受字段权限约束。

平台全量数据范围要求有效 admin 角色；普通角色即使有 package:* 也不能因此读取租户全部应用。保留有效租户成员和单一有效业务身份的入口校验。管理员仍不跨租户、不访问未登记归属的数据。

查询/编辑使用所有者或共享关系；删除、共享管理、关联资源创建等继续要求所有者或管理员。编辑事务内锁定当前归属和共享关系，再确认授权，以保证撤销共享后不能靠旧页面继续保存。共享批量提交必须全部授权、全部成功或全部回滚，重复授权幂等。删除应用同步清理共享关系，保留审计。

## 接口与页面

沿用 package:apps:transfer 作为共享管理权限，页面改称“共享应用”。新增 POST /package-admin/apps/shares，body 为 {ids,targetUser,reason}；GET /package-admin/apps/{id}/shares 返回 {records,total}，每条包含 userId、displayName、grantedBy、reason、createdAt；POST /package-admin/apps/shares/revoke 为 {ids,targetUser,reason}；GET /package-admin/apps/{id}/share-audit 返回 {records,total}。新增及撤销操作返回变更数量；原因必填、最多500字符；批量1至100个不同正整数ID。历史 /apps/transfer 保留为同一共享语义的兼容入口，缺少原因时记录兼容入口默认原因；禁止继续执行更换归属。

应用返回 canManage 布尔值（当前用户为所有者或管理员），服务端每次计算，不接受请求伪造。前端用此值配合按钮权限隐藏接收者的删除/共享管理操作，混合批量选择禁止删除及共享。共享弹窗允许选择租户内有效业务成员，显示权限边界；单行共享管理显示接收者、撤销入口和审计。请求过期保护、失败保留输入、重复提交锁。

共享审计新增 pkg_app_share_audit，记录操作人、租户、应用、接收人、GRANT/REVOKE、原因和时间；与共享写入同事务。时间和大编号作为字符串输出。撤销不删除应用或更改创建者。接收者共享给自己或所有者不产生无意义关系。普通用户不能管理收到的共享，即使其角色有 transfer/remove。

## 升级和历史限制

新增 014-app-sharing.sql 及菜单文字升级，保留旧权限标识和授权，不自动授予普通角色权限。重复执行不丢数据。旧版真正转移过的数据保留当前归属，不能猜测原创建者；需要人工核对后单独修复。新共享不自动共享统计、上架、PWA等关联数据。本地实现验证，不部署线上、不修改实际用户权限、不自动提交Git。

## 验收

真实MySQL覆盖创建者/接收者/第三人/管理员/跨租户、编辑后归属不变、普通通配角色不可越权、接收者删除/转授403、撤销后查询和编辑拒绝、事务回滚、批量混合与重复授权、关联资源隔离、审计和迁移幂等。前端组件测试覆盖按钮及批量资格、共享撤销、异步和错误；执行后端完整回归、前端测试、生产构建及候选服务HTTP验收。
